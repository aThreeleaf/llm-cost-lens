# LLM Cost Lens：AI 协作开发记录

本文档记录 LLM Cost Lens 项目从零到完成部署过程中，真实的 AI 辅助研发（AI-assisted development）全流程。

这不是一份工具堆砌的清单，也不是概念宣传。其核心目的是复盘：
- 各角色（人类开发者与不同 AI）的真实分工与协作边界
- 哪些关键产品与交互方案经过人工判断后被推翻或重构
- 如何通过跨模型独立 Review 发现真实缺陷并形成工程闭环
- 如何识别并纠正 AI 生成内容中的“合理幻觉”与事实偏差

---

## 1. 项目起点与 MVP 定义

项目立项之初，最关键的第一步是**严格定义问题边界与范围控制（Scope Control）**。

经过与 ChatGPT 的讨论与需求拆解，我们明确了当前工具的核心诉求非常纯粹：
> **用户输入单次请求的输入/输出 Token 数及每日请求频率，快速横向对比主流大模型 API 的预估花费。**

当前需求仅涉及前端输入响应、模型价格换算以及列表排序与渲染，不存在用户系统、数据持久化或复杂的跨页面状态管理。因此，项目无需引入任何前端框架或后端服务，而是直接采用最简洁的技术方案：
- **HTML5 + CSS3 + Vanilla JavaScript (ES2022+)**
- **零后端、零数据库、零构建打包流程、零 npm 运行时依赖**
- **静态部署于 Netlify**

这是基于当前实际需求的范围控制，避免为了未来可能不存在的扩展而提前引入不必要的架构复杂度。

---

## 2. 第一版实现与人工判断

在技术栈确定后，Antigravity 完成了第一版可运行原型，包括输入表单、基础价格展示和成本计算。

然而，在人类开发者实际打开页面体验后，发现了一个明显的用户体验问题：
- 将所有厂商的全部模型卡片平铺在一个视图中，导致单屏信息密度极度过载。
- 用户很难直观对比“同品牌内部各梯队”或者“跨品牌目标模型之间”的差异。

人类开发者没有直接接受这一版看似“功能齐全”的实现，而是立即叫停并提出重构交互方案，将比价拆分为两个独立模式：
1. **同品牌对比（Same provider）**：先选定一个厂商（如 OpenAI），再在该厂商下自由勾选模型（如 Luna vs Sol vs Astra）。
2. **跨品牌对比（Cross provider）**：跨厂商自由勾选多个模型进行统一比较。

在此过程中，还出现了一个关键的**人工产品决策**：
> 初始讨论曾考虑“在跨品牌模式下，每个厂商只能选择一个模型”。但人类开发者从真实比价需求出发推翻了这一设想——实际开发者在选型时，往往需要同时对比“Google 的高性价比模型 + 旗舰模型”与“Anthropic 的对应梯队模型”。人为限制单选完全脱离实际需求，因此最终决定在跨品牌模式下依然允许对任意厂商进行多选。

这个决策由人类根据真实业务理解做出，直接决定了最终产品的易用性。

---

## 3. 定价数据与范围控制

项目最终收录了 **4 大主流供应商（OpenAI、Anthropic、Google、xAI）共 22 款模型**。

定价数据采集与实现遵循严格的真实性原则：
- **数据来源**：定价数据依据各厂商官方文档人工核验，核验日期为 2026-09-04。
- **长上下文阶梯定价（Long-context pricing）**：OpenAI 部分模型在 >272k 时切换费率，Gemini 3.1 Pro Preview 在 >200k 时切换，当前 xAI 模型在 >=200k 时切换。
- **克制设计**：没有为了所谓的“通用性”去手写一套复杂的抽象规则引擎（Rule Engine），而是紧扣各厂商当前已落地的实际规则编写纯函数映射，确保逻辑清晰且易于维护。

## 4. 独立 QA

核心功能开发完毕后，项目并未直接发布上线，而是引入 **Codex 作为独立 Reviewer** 进行代码审查与边界测试。

这一步打破了由同一模型“既当裁判又当选手”的局限性。Codex 独立审查后给出了评级报告：
- **CRITICAL**：None
- **HIGH**：None
- **MEDIUM**：1 个
- **LOW**：2 个

其中发现了一个真实的边界计算缺陷（MEDIUM）：
> `parseNonNegativeNumber()` 虽然能防御负数和 NaN，但允许极大的有限数字输入（例如 `1e308`）。后续执行乘法与累加运算时，中间变量 `costPerRequest`、`costPerDay`、`cost30Days` 会直接溢出为 JavaScript 的 `Infinity`。这导致页面卡片渲染出 `$Infinity` / `$Infinity.00`，并彻底破坏了最低成本（Lowest cost）的判断逻辑。

## 5. Bug 修复决策

针对 Codex 发现的计算溢出问题，修复策略的选择再次体现了**工程理性与人工判断**：

- **方案 A（人为硬编码上限）**：直接限制 `max tokens = 10000000` 或 `max requests = 1000000`。  
  *评估*：被人工否决。因为不同业务场景（如离线超长文本批处理、高频轻量接口仿真等）差异极大，产品层面没有任何依据去主观规定一个数字上限。
- **方案 B（结果级数学有限性校验）**：保持现有解析规则，在 `selectedModels.map(calculateModelCost)` 完成之后、进入排序与渲染之前，统一检查所有金额指标的 `Number.isFinite()`。  
  *评估*：采纳。若存在溢出，立即阻断排序与卡片渲染，在模型对比区域优雅呈现空状态提示：
  - English：`Input is too large to calculate safely.`
  - 中文：`输入值过大，无法安全计算。`

当用户将输入恢复为合法数值后，对比列表即刻自动恢复。该方案不需要人为设定业务上限，同时可以避免非有限计算结果进入排序和渲染流程。

---

## 6. 独立复审

修复完成后，代码再次提交给 Codex 进行针对性复审，严格限定复审范围为原缺陷验证与回归风险评估。

复审结果：
- **Original MEDIUM Issue**：RESOLVED
- **Regression Introduced**：NO
- **Final Verdict**：PASS

至此，团队完成了：
$$\text{实现（Antigravity）} \longrightarrow \text{独立评审（Codex）} \longrightarrow \text{针对性修复} \longrightarrow \text{回归复审（PASS）}$$
的完整的 implementation → review → fix → re-review 闭环。

## 7. 文档阶段中的 AI 错误

在后续编写项目文档时，团队记录了一个非常典型的 **AI 事实偏差（幻觉）案例**：

在 Antigravity 首次生成 `README.md` 的模型清单时，AI 生成的 xAI 模型列表中出现了：
- `Grok 4 Fast`
- `Grok 3`
- `Grok 3 Mini`

然而，项目 [script.js](../script.js) 中实际收录并校验过的真实 xAI 模型为：
- `Grok Build 0.1`
- `Grok 4.3`
- `Grok 4.20 Multi-Agent`

尽管 AI 生成的模型名称“看起来非常真实且符合命名直觉”，但人类开发者在审阅过程中没有被表面合理性误导，而是直接对照代码真实来源（Source of Truth），及时抓出了这一偏差并强制进行了校正。

这一案例深刻说明：**即使到了项目收尾与文档阶段，人类把关依然不可或缺，任何涉及事实性数据的输出都必须有依据可查。**

## 10. 总结与思考

通过 LLM Cost Lens 的完整开发历程，我们对“AI 辅助研发（AI-assisted Development）”有了更深刻的理解：

AI 辅助研发绝不是简单地**“将需求一股脑抛给 AI，然后全盘接受生成的代码”**。

在现代工程实践中，它是一种新型的人机协同模式：
1. **人类把舵**：决定不做什么比决定做什么更重要，时刻把控项目范围与真实业务价值；
2. **AI 提效**：利用智能体完成快速原型验证、模板代码编写和细节实现；
3. **交叉制衡**：通过不同 AI 工具承担实现与审查角色，降低单一工具自审带来的盲区；
4. **事实锚定**：对一切文档、价格、清单进行严格的事实溯源与人工核验；
5. **责任在人**：最终的系统质量、边界安全、用户体验与交付责任，始终且必须由人类工程师承担。
