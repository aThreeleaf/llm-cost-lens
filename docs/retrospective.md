# 从需求到上线：我如何用 AI 协作完成 LLM Cost Lens

作为一个经常需要调用不同大语言模型 API 的开发者，我经常面临一个很现实的选型困扰：各家厂商的定价单位都是“每百万 Token 几美元”，但不同模型的输入与输出价格比例各不相同，长上下文还会有隐性的阶梯涨价。在实际业务中，单次请求到底花多少钱？如果每天调用 1000 次，一个月下来账单会是多少？

为了解决这个直观却又琐碎的算账痛点，我完成了 **LLM Cost Lens**——一个纯浏览器端的模型 API 成本估算与对比工具。

在这个项目中，我全程采用了 AI 辅助研发模式（ChatGPT 参与需求探讨、Antigravity 负责主力编码、Codex 负责独立审查与 QA）。回顾从零构思、交互推翻、缺陷修复到最终上线的完整过程，我记录下这篇复盘，重点不是罗列工具，而是聊聊我在这个过程中做了哪些判断、踩了哪些坑，以及我如何看待人机协同的边界。

---

## 1. 项目目标与问题定义

在动工前，我给这个工具定下的核心目标非常聚焦：
- 用户输入：单次请求的输入 Token、输出 Token，以及每日预估请求次数。
- 工具输出：实时计算并展示各模型的单次请求成本、每日成本以及 30 天预估总额，并自动标识出成本最低的选项。
- 覆盖范围：主流 4 大供应商（OpenAI、Anthropic、Google、xAI），共收录 22 款模型。

工具的本质是一个帮助开发者在上线前评估预算的决策助手。明确了这一目标后，后续所有功能开发都严格围绕这个主线展开，不蔓不枝。

---

## 2. 技术选型：克制与“刚刚好”

在技术选型阶段，我评估了是否需要引入前端框架和构建工具。仔细拆解功能需求后：
这是一个纯粹的浏览器端工具，核心逻辑全部是确定性的数学计算、动态输入监听、模型多选筛选与卡片排序，完全没有用户鉴权、数据库读写、跨设备状态同步或复杂路由跳转。

如果引入框架和构建工具，用户每次打开页面都需要加载额外的运行时体积；而对于我而言，还要承受 npm 依赖更新、构建打包配置和潜在的供应链安全风险。

因此，我做出了一个坚决的决定：**使用原生的 HTML5、CSS3 和纯 JavaScript（ES2022+）**。
- 零框架、零构建、零 npm 依赖；
- 静态部署在 Netlify 上，任何现代浏览器双击 `index.html` 就能直接离线运行。

这并不是为了刻意追求“极简主义”的形式感，而是基于真实需求做出的理性裁剪：**技术栈越复杂，绝不代表方案越优秀；能够用最直接、依赖最少的方式彻底解决问题，才是更好的工程选择。**

---

## 3. 交互推翻：AI 可以快速写代码，但不能代替我判断体验

在核心计算逻辑跑通后，Antigravity 很快生成了第一版可运行原型。这一版把所有支持的模型卡片全部平铺在网格中，输入数值后卡片金额实时刷新，功能完全正常。

但我自己打开网页实际操作了几分钟后，就发现了严重的问题：
把大量模型卡片铺满整个屏幕，信息密度极高，满屏都是数字。当我想对比“OpenAI 内部各梯队模型的差价”时，视线必须在网格里到处跳跃；而当我想对比“各大厂旗舰模型的差价”时，又被海量的轻量模型干扰。

功能虽然“能用”，但体验不及格。我没有直接采纳这个版本，而是停下来重新梳理交互，设计了双模式比价逻辑：
- **同品牌对比（Same provider）**：先选定厂商，再在厂商内部自由勾选不同模型，方便在同一生态内看阶梯性价比；
- **跨品牌对比（Cross provider）**：按厂商分组呈现实体复选框，支持跨厂商自由挑选目标模型进行全网横向 PK。

在这个过程中，我们曾讨论过一个设想：“在跨品牌模式下，是否限制每个厂商只能选 1 个代表模型，避免界面太乱？”
我根据真实的选型经验否决了这个限制：很多时候开发者在选型时，恰恰需要同时把 Google 的轻量版与旗舰版，拿来和 Anthropic 的轻量版与旗舰版放在一起综合评估。限制单选脱离了真实的业务习惯。

最终证明，这个由人类主导的交互重构决定，彻底改变了产品的可用性。**AI 能够极速产出可工作的代码，但交互逻辑到底顺不顺手、符不符合人的心智模型，必须由开发者亲自把关与修正。**

---

## 4. 定价数据：只解决当下真实存在的规则

工具收录了 4 个厂商的 22 款模型，定价数据依据各厂商官方定价文档人工核验，核验日期为 2026-09-04。

在实现过程中，一个技术细节是长上下文阶梯定价（Long-context pricing）：
- OpenAI 部分模型在输入大于 272k 时加价；
- Gemini 3.1 Pro Preview 在大于 200k 时加价；
- xAI 部分模型在大于等于 200k 时加价。

在处理这块逻辑时，很容易产生一种“过度设计”的冲动——比如提前写一套复杂的抽象规则引擎，去支持未来可能出现的各种花哨计费模式。

但我提醒自己保持克制：不同大厂的阶梯规则目前差异很大，且各自处于变动期，过早抽象只会创造臃肿且难以维护的死代码。最终我选择只针对当前已经落地的规则编写纯函数逻辑，在计算前动态决定生效单价。**不为未知的未来过度设计，只扎实解决当下真实存在的问题。**

## 5. 独立 QA 与边界处理：能跑通不代表算对了

当核心功能与多语言适配全部完成后，我没有急于部署上线，而是引入 Codex 作为独立 Reviewer 对代码进行审查与边界测试。

这次审查抓出了一个容易被忽略的边界 Bug（MEDIUM 级）：
在输入解析函数中，虽然排除了负数和 NaN，但 JavaScript 允许合法的极端大数输入（如 `1e308`）。在后续将输入 Token、单价与请求次数进行连续乘法累加时，中间变量会直接发生浮点数溢出，变成 `Infinity`。
结果是：页面赫然展示出 `$Infinity` 和 `$Infinity.00`，且最低成本的高亮逻辑被彻底打乱。

对于这个 Bug，最省事的修复方案莫过于在前端输入框随手写死一个 `max="10000000"`。但我认为这个改法是不合理的，当前没有业务依据去人为规定一个最大允许输入值。

因此，我选用了在计算结果层进行数学有限性校验的方案：
在成本计算完成后、进入排序和渲染前，用 `Number.isFinite` 检查每项费用指标。只要检测到计算溢出，立即阻断后续排序与卡片渲染，优雅展示提示信息：
- 英文：`Input is too large to calculate safely.`
- 中文：`输入值过大，无法安全计算。`

当用户把输入改回合法数值后，模型卡片立即恢复显示。修复后提交 Codex 针对性复审，最终获得全面 PASS。

**功能在常规输入下“跑得通”，绝不代表边界条件已经处理严谨。引入异构 AI 工具作为独立审计者，能非常有效地帮开发者跳出自审的思维盲区。**

## 6. 文档审查：AI 也会产生“合理的幻觉”

在进入交付阶段编写 README 时，发生了一件很有代表性的事情：
Antigravity 在初次起草的文档中列出了 xAI 的模型清单，看起来极其整齐自然，包含了 `Grok 4 Fast`、`Grok 3`、`Grok 3 Mini` 等名字。

然而，当我习惯性地打开代码库里的真实源头（`script.js` 中的 `MODEL_PRICING`）逐字核对时，猛然发现代码里实际录入的明明是 `Grok Build 0.1`、`Grok 4.3`、`Grok 4.20 Multi-Agent`。

这些名称看起来合理，但与项目中的真实 Source of Truth 不一致。我立刻人工修正了这一处事实偏差。

这件事给我的警示是：**AI 的输出即使再流畅、再合乎逻辑，只要涉及事实性、枚举型的数据，就必须拿真实源头去逐字对账。人类不能因为 AI 编写代码的能力强，就放弃了对事实数据的审校责任。**

## 8. 最终思考：让 AI 提高执行速度，但不把判断权交出去

从产生构想到最终把 LLM Cost Lens 推送到线上，整个过程让我对“AI 协作”有了非常清晰的认知沉淀。

AI 辅助编程最大的价值，不是让我彻底“放手不管”，而是形成了一套极其敏捷的高效闭环：
$$\text{定义问题与边界} \longrightarrow \text{AI 快速原型实现} \longrightarrow \text{人类评估体验与重构} \longrightarrow \text{异构 AI 独立 Review} \longrightarrow \text{针对性修复} \longrightarrow \text{人工严密验证与验收}$$

在这个工作流中：
- AI 负责快速实现 DOM 交互、样式细节和重复性编码工作；
- 独立 AI 负责站在对立视角挑刺、挖掘边界异常和测试盲点；
- 而我作为开发者，负责**把控范围（决定什么不做）、裁决产品体验、核实数据真伪、权衡工程取舍，并对最终交付的质量负全责**。

**让 AI 提高执行速度，但不把判断权交出去。** 这就是我完成 LLM Cost Lens 最宝贵的体会。
