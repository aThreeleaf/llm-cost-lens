# 从需求到上线：我如何用 AI 协作完成 LLM Cost Lens

## 1. 我做了什么

这次我完成了 **LLM Cost Lens**，一个纯浏览器端的 LLM API 成本估算与比较工具。用户输入每次请求的 Input Tokens、Output Tokens 和 Requests/day 后，页面会实时计算各模型的单次请求成本、每日成本和 30 天预估成本，并按成本排序、标出最低成本选项。

项目最终支持 OpenAI、Anthropic、Google、xAI 四个 Provider，共 22 款模型，并提供 Same provider 和 Cross provider 两种比较模式。Same provider 用于同一厂商内部多模型比较；Cross provider 则允许用户跨多个 Provider 自由选择多个模型，而不是限制每个品牌只能选一个。

技术上我最终选择 HTML5、CSS3 和 Vanilla JavaScript，没有引入 React、后端、数据库或 npm 依赖。原因不是刻意追求“极简”，而是这个问题本质上就是浏览器端的输入响应、价格计算、筛选、排序和展示。对当前需求而言，静态前端已经足够，额外架构只会增加实现和维护成本。项目最终通过 Netlify 部署，并补齐了双语 README、项目截图、官方 Pricing Sources、Known Limitations、AI 协作记录和公开复盘页面。

## 2. 我踩了什么坑

第一个坑不是代码报错，而是“功能能跑，但体验不好”。早期版本会同时展示大量模型卡片，输入数值后金额也能正常更新，但真正打开页面使用时，我发现信息密度太高。想看同一厂商内部不同梯队的价格差异，或者只比较几个目标模型时，都需要在大量卡片中寻找。

因此我没有把“能运行”当作完成，而是重新设计交互，把比较拆成 Same provider 和 Cross provider。过程中还讨论过“Cross provider 每个 Provider 是否只允许选一个模型”，但我最终否决了这个限制，因为真实选型时完全可能同时比较同一厂商的轻量模型和旗舰模型，再与其他厂商的多个模型横向比较。最终保留了真正的多模型自由选择。

第二个坑来自边界输入。核心功能完成后，我让 Codex 独立做代码 Review 和边界测试。它发现当用户输入 `1e308` 这样的极端大但仍为有限数值的输入时，JavaScript 后续乘法可能把 `costPerRequest`、`costPerDay`、`cost30Days` 计算成 `Infinity`，页面会出现 `$Infinity` / `$Infinity.00`，Lowest cost 判断也会受到影响。

我没有简单给输入框写一个随意的最大值，因为当前没有业务依据说明“最大合法输入”应该是多少。最终的处理方式是在成本计算完成后、排序和渲染之前，用 `Number.isFinite` 检查计算结果；发现溢出就停止金额卡片渲染并提示用户输入过大。修复后再交给 Codex 做针对性复审，最终 PASS。这个问题让我意识到：常规输入下能跑通，不代表边界条件已经正确。

## 3. AI 在哪里帮了我

这个项目里我主要用了 ChatGPT、Antigravity 和 Codex。ChatGPT 更多参与需求拆解、产品方案讨论、范围控制、阶段审查和测试思路；Antigravity 负责主要 HTML/CSS/JavaScript 实现、交互开发和 Bug 修复；Codex 则承担独立代码 Review、边界测试和修复后的定向复审。

AI 对我最大的帮助不是“替我把整个项目做完”，而是显著缩短了从想法到可运行版本的周期。一个交互方案可以很快被实现，我马上就能打开真实页面体验，再决定保留、修改还是推翻。这样产品判断不再停留在纸面讨论，而是可以建立在真实运行结果上。

把实现和 Review 分给不同工具也很有价值。Antigravity 负责实现后，再让 Codex 从独立 Reviewer 的角度寻找边界问题，比让同一个工具自查更容易暴露遗漏。Infinity 问题就是在这个过程中发现的。

## 4. AI 在哪里坑了我

AI 也给过我看起来很合理、实际上却错误的结果。

在 README 阶段，Antigravity 曾把 xAI 模型列表写成 `Grok 4 Fast`、`Grok 3`、`Grok 3 Mini` 等名称。单独看这些名字并不突兀，但我重新对照 `script.js` 中的 `MODEL_PRICING` 后发现，它们与项目真正使用的数据不一致。代码里的实际模型包括 `Grok Build 0.1`、`Grok 4.3`、`Grok 4.20 Multi-Agent` 等。

最终我以 `MODEL_PRICING` 作为 Source of Truth 修正了 README。这个错误对我提醒很大：AI 输出“读起来合理”和“事实正确”是两回事。尤其是模型名称、价格、阈值、枚举列表这类事实型数据，不能因为文本流畅就直接接受，必须回到真实数据源逐项核对。

价格本身也需要保持这种谨慎。当前价格是我在 2026-09-04 根据各厂商官方文档核验的快照，未来厂商价格和计费规则可能变化，而且项目明确没有覆盖缓存价格、Batch 折扣、工具调用等额外费用，所以这个工具给出的始终是估算结果，而不是最终账单。

## 5. 下次我怎么做得更快

如果再做一次类似项目，我会把“验收”提前，而不是等功能基本完成后再集中检查。项目一开始就建立一份固定 checklist：核心计算公式、长上下文阈值边界、0/空值/极端输入、中英文切换、移动端布局、README 与代码数据一致性，以及最终公网链接的无痕访问。

我也会更早把实现者和 Reviewer 分开，让 Antigravity 负责实现、Codex 更早介入独立 Review，而不是等到后期再一次性检查。这样边界问题可以更早暴露，减少后期返工。

另一个可以明显提速的地方，是更早固定唯一的 Source of Truth。模型名称、价格和长上下文阈值都应该始终以 `MODEL_PRICING` 为准，文档中出现这些数据时也必须从同一来源核验，避免像 README 模型列表那样出现人工或 AI 复制不一致。

最后，我会更早做真实页面体验。这个项目里最重要的一次产品改动，恰恰不是来自代码错误，而是我真正打开页面后发现“所有模型一起展示”不好用。以后我会在每个可运行阶段都尽快体验真实页面，而不是只看代码是否通过。

这次项目让我形成了一套更清晰的 AI 协作方式：

**定义问题与边界 → AI 快速实现 → 人工体验和判断 → 独立 Review → 针对性修复 → 再验证。**

AI 可以提高执行速度，但 Scope、产品判断、事实核验和最终质量，仍然需要开发者自己负责。对我来说，最重要的不是让 AI 替我做决定，而是让 AI 加快执行，同时把判断权留在自己手里。
